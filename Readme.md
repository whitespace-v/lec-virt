# Лекция 3. Виртуализация и контейнеризация

> Сквозной сценарий лекции: у нас есть образ веб-приложения, из которого мы
> запускаем контейнер `web-42`. Всю лекцию мы будем доказывать одну простую, но
> неочевидную мысль: **контейнер — это не «лёгкая виртуалка», а обычный процесс
> Linux, которому ядро подсунуло изолированное окружение.** Мы разберём `web-42`
> по винтикам, соберём похожий контейнер руками без Docker, а потом поднимемся до
> systemd и Kubernetes. В конце — вопросы, держите `web-42` в голове.
>
> Эта лекция опирается на две предыдущие: **namespaces** здесь — прямое
> продолжение сетевых namespace из лекции про сеть, а **user namespaces и
> capabilities** — из лекции про права. Если что-то из этого подзабылось, самое
> время подсмотреть.

---

## 0. Главный вопрос лекции

Про контейнеры ходит три мифа, и мы весь урок будем их опровергать:

1. «Контейнер — это лёгкая виртуальная машина».
2. «Внутри контейнера своё ядро/своя ОС».
3. «Docker — это какая-то магия».

Спойлер: всё три неверны. Чтобы понять почему, начнём с честного сравнения
виртуализации и контейнеризации — они решают похожую задачу (изолировать
приложения), но принципиально по-разному.

---

## 1. Виртуализация: честная, но тяжёлая изоляция

**Виртуальная машина (ВМ)** — это эмуляция целого компьютера. На физической
машине работает **гипервизор**, который создаёт виртуальное «железо», а поверх
него ставится **полноценная гостевая ОС со своим ядром**.

Бывают два типа гипервизоров:

- **Тип 1** («bare-metal») — работает прямо на железе: KVM (в Linux), VMware
  ESXi, Hyper-V. Так делают в дата-центрах.
- **Тип 2** — работает как программа внутри обычной ОС: VirtualBox, VMware
  Workstation. Так вы запускаете Linux внутри Windows на ноутбуке.

Ключевая картинка виртуализации:

```
┌─────────────┐ ┌─────────────┐   каждая ВМ несёт
│   Прил. A   │ │   Прил. B   │   ПОЛНОЕ гостевое ядро
├─────────────┤ ├─────────────┤   и всю ОС целиком
│ Гостевое    │ │ Гостевое    │
│ ядро+ОС     │ │ ядро+ОС     │
├─────────────┴─┴─────────────┤
│         Гипервизор          │
├─────────────────────────────┤
│      Хостовое ядро/железо    │
└─────────────────────────────┘
```

Плюсы: **настоящая** изоляция (у каждой ВМ своё ядро — соседи вообще не видят
друг друга) и можно запускать другую ОС (Windows на Linux-хосте). Минусы:
**тяжело**. Каждая ВМ тащит с собой целую ОС — это гигабайты диска, отдельная
загрузка ядра, минуты на старт, ощутимый расход памяти. Запустить так 50 мелких
сервисов — расточительно.

Отсюда возникает идея: а что если приложениям **не давать своё ядро**, а
заставить их делить одно ядро хоста — но так, чтобы они друг друга не видели?

---

## 2. Контейнеризация: делим ядро, изолируем окружение

**Контейнер** использует ядро хоста напрямую. Никакого гостевого ядра,
никакого эмулированного железа. Изолируется только **пространство пользователя**
(userspace): процессы, файловая система, сеть — но не ядро.

```
┌─────────┐ ┌─────────┐ ┌─────────┐   контейнеры — просто
│ web-42  │ │ Прил. B │ │ Прил. C │   изолированные процессы,
├─────────┴─┴─────────┴─┴─────────┤   БЕЗ своего ядра
│        Хостовое ядро (одно!)     │
├─────────────────────────────────┤
│            Железо               │
└─────────────────────────────────┘
```

Сравните две схемы. В виртуализации ядро у каждого своё; в контейнеризации ядро
**одно на всех**, а изоляцию обеспечивают механизмы этого ядра. Отсюда: контейнер
стартует за миллисекунды (это же просто запуск процесса), весит мегабайты, а не
гигабайты. Плата — изоляция слабее (общее ядро — общая точка отказа) и нельзя
запустить чужую ОС (на Linux-ядре не будет Windows-контейнера с настоящим
Windows).

Убедимся, что контейнер действительно делит ядро с хостом. Спросим версию ядра
внутри `web-42` и на хосте:

```bash
uname -r                              # версия ядра на хосте
docker exec web-42 uname -r           # версия ядра ВНУТРИ контейнера
```

```
6.8.0-45-generic        ← хост
6.8.0-45-generic        ← внутри web-42, ТА ЖЕ САМАЯ
```

Версии **идентичны** — потому что ядро буквально одно и то же. Это первый гвоздь
в миф «внутри контейнера своя ОС»: userspace может быть другим (внутри может быть
Alpine, снаружи Ubuntu), но ядро всегда хостовое.

Теперь разберёмся, *какие именно* механизмы ядра создают иллюзию отдельной
системы. Их три: **namespaces**, **cgroups** и **capabilities**.

---

## 3. Namespaces: «что процесс видит»

**Namespace** отвечает на вопрос «что процесс видит». Ядро умеет дать процессу
изолированный вид на тот или иной ресурс. Видов namespace несколько:

| Namespace | Что изолирует |
|---|---|
| `pid` | дерево процессов (свои PID) |
| `net` | сеть (интерфейсы, маршруты) — **это из прошлой лекции!** |
| `mnt` | точки монтирования (своя файловая система) |
| `uts` | hostname |
| `ipc` | межпроцессное взаимодействие |
| `user` | отображение UID/GID — **связь с лекцией про права** |
| `cgroup` | вид на cgroup-иерархию |

Мы уже вплотную работали с `net` namespace в прошлой лекции, когда руками строили
veth-пару. Теперь посмотрим на `pid` — он даёт самый наглядный эффект.

Заглянем, что видит `web-42` в своём дереве процессов:

```bash
docker exec web-42 ps aux             # список процессов ВНУТРИ контейнера
```

```
USER   PID  COMMAND
root     1  /usr/bin/my-web-app       ← наше приложение имеет PID 1
root    14  ps aux
```

Внутри контейнера приложение имеет **PID 1** — как будто это первый процесс во
всей системе. Внутри `web-42` кажется, что кроме него и пары служебных процессов
вообще ничего не запущено. Но это иллюзия pid namespace. Посмотрим на **тот же
самый** процесс с хоста:

```bash
ps aux | grep my-web-app              # ищем процесс приложения на ХОСТЕ
```

```
USER      PID   COMMAND
root    48231   /usr/bin/my-web-app
```

На хосте у этого же процесса PID **48231**, и он стоит в общем ряду с сотнями
других процессов машины. **Один и тот же процесс, два разных PID** — 1 внутри и
48231 снаружи. Никакой отдельной системы нет: `web-42` — это процесс 48231 на
хосте, которому pid namespace показывает мир так, будто он там первый и
единственный. Второй гвоздь в миф про «отдельную ОС».

Проверим ещё и hostname (uts namespace):

```bash
docker exec web-42 hostname           # имя хоста внутри контейнера
hostname                              # имя хоста снаружи
```

```
a1b2c3d4e5f6      ← внутри (Docker выдал случайное)
learnserver       ← снаружи, наш реальный сервер
```

Разные — потому что uts namespace даёт контейнеру собственный hostname, не
затрагивая хостовый.

## 4. Cgroups: «сколько процессу можно»

Namespaces отвечают «что видно». **Cgroups** (control groups) отвечают на другой
вопрос — «**сколько ресурсов можно** потреблять»: сколько CPU, памяти, операций
диска. Без cgroups один контейнер мог бы съесть всю память машины и уронить
соседей.

Запустим `web-42` с лимитом памяти и проверим:

```bash
docker run -d --name web-42 --memory=256m -p 8080:8080 my-web-app
docker exec web-42 cat /sys/fs/cgroup/memory.max   # какой лимит памяти видит контейнер
```

```
268435456
```

`268435456` байт = ровно 256 МиБ. Мы ограничили контейнер: даже если приложение
сойдёт с ума и попытается занять всю память сервера, ядро не даст ему выйти за
256 МиБ (при превышении процесс будет убит OOM-killer'ом). Так один сервис
защищён от другого.

> Небольшая историческая деталь: у cgroups есть две версии — v1 и v2. В v1
> каждый вид ресурса жил в своей иерархии, в v2 всё объединено в одну (пример
> выше — из v2, отсюда единый путь `/sys/fs/cgroup/`). Современные системы на v2.

Важная связка: **каждый контейнер = свой cgroup**. Именно через cgroups работает
`docker stats` — он просто читает счётчики потребления из cgroup контейнера. И —
забегая вперёд — точно так же systemd помещает каждый сервис в свой cgroup
(раздел 8).

## 5. Capabilities: root, разобранный на части

Из лекции про права вы помните: `uid=0` (root) может всё. Но «всё» — это на
самом деле набор из ~40 отдельных разрешений, которые называются
**capabilities**. Например:

- `CAP_NET_BIND_SERVICE` — право занять порт ниже 1024;
- `CAP_NET_ADMIN` — настраивать сеть;
- `CAP_SYS_ADMIN` — почти всемогущество (много всего);
- `CAP_CHOWN` — менять владельца файлов.

Полноценный root на хосте имеет их все. А контейнеру Docker по умолчанию выдаёт
**урезанный** набор — чтобы даже root **внутри** контейнера не мог навредить
хосту.

```bash
docker exec web-42 whoami                    # кто мы внутри контейнера
```

```
root
```

Внутри мы root! Но давайте проверим, настоящий ли это всемогущий root. Попробуем
из-под него изменить системное время (для этого нужен `CAP_SYS_TIME`):

```bash
docker exec web-42 date -s "2030-01-01"      # пробуем перевести системные часы
```

```
date: cannot set date: Operation not permitted
```

**Отказано** — хотя мы root! Docker не выдал контейнеру `CAP_SYS_TIME`. Вот и
третий важный вывод: root внутри контейнера — это не тот же root, что на хосте.
Это «root с урезанными полномочиями».

И самая надёжная защита — **user namespace** (помните из лекции про права?): он
может отобразить `uid=0` **внутри** контейнера на обычный непривилегированный
UID (например, 100000) **снаружи**. Тогда даже если процесс как-то вырвется из
контейнера, на хосте он окажется бесправным пользователем 100000, а не root'ом.
Это прямое применение user namespace, о котором шла речь в первой лекции.

## 6. Собираем контейнер руками, без Docker

Пришло время главного доказательства, что «Docker — не магия». Соберём подобие
контейнера **одной командой ядра** `unshare`, которая создаёт новые namespaces
для процесса. Ни Docker, ни containerd — только ядро.

```bash
# создаём процесс в новых namespace: pid, mount, uts, а также свой /proc
sudo unshare --pid --mount --uts --fork --mount-proc bash
```

Разберём флаги: `--pid` — свой pid namespace, `--mount` — своя таблица
монтирования, `--uts` — свой hostname, `--fork` — запустить дочерний процесс в
этих namespace, `--mount-proc` — смонтировать свежий `/proc` (чтобы `ps`
показывал только «наши» процессы). После этой команды мы **внутри** — приглашение
сменилось на новый bash. Поменяем hostname и посмотрим на процессы:

```bash
# теперь мы ВНУТРИ нашего самодельного "контейнера"
hostname my-manual-container          # меняем hostname (сработает только внутри uts ns)
ps aux                                # смотрим процессы в нашем pid namespace
```

```
USER   PID  COMMAND
root     1  bash                      ← наш bash имеет PID 1!
root     8  ps aux
```

Узнаёте картину? Наш `bash` получил **PID 1** — ровно как `my-web-app` внутри
`web-42` в разделе 3. Мы своими руками, одной командой, воспроизвели главный
эффект контейнера: изолированное дерево процессов, где мы — первый процесс.
И hostname сменился только внутри, хост об этом не знает.

Проверим изоляцию с другой стороны — откроем **второй** терминал на хосте и
найдём наш bash:

```bash
# в ДРУГОМ терминале, на хосте
ps aux | grep '[b]ash' | grep -v grep    # ищем наш "контейнерный" bash снаружи
```

```
root    51002   unshare --pid --mount --uts --fork --mount-proc bash
root    51003   bash
```

Снаружи наш «PID 1» — это обычный процесс с PID **51003**. Ровно та же история,
что с `web-42` (PID 1 внутри = 48231 снаружи). Мы наглядно показали: контейнер =
процесс + namespaces. Docker добавляет к этому удобство (образы, сеть, лимиты),
но фундамент — вот эта одна команда `unshare`.

## 7. Что на самом деле делает Docker

Теперь, когда «магия» разоблачена, разложим Docker на слои. Когда вы пишете
`docker run`, срабатывает цепочка:

```
docker (CLI)  →  dockerd  →  containerd  →  runc  →  [namespaces + cgroups]
   вы           демон-      менеджер      создаёт    примитивы ядра
                сервер      контейнеров   контейнер   (то, что мы делали руками)
```

- **docker (CLI)** — то, что вы набираете в терминале. Просто отправляет команду
  демону.
- **dockerd** — фоновый демон, принимает команды, управляет образами и сетями.
- **containerd** — управляет жизненным циклом контейнеров (запуск, остановка).
- **runc** — самый нижний уровень: именно он вызывает `clone`/`unshare` и
  настраивает cgroups. **runc делает ровно то, что мы делали руками в разделе 6.**

Всё это стандартизировано спецификациями **OCI** (Open Container Initiative):
отдельно описан формат образа (image-spec) и формат запуска (runtime-spec).
Именно благодаря стандарту образ, собранный Docker, можно запустить другим
инструментом — все они говорят на языке OCI.

А что такое сам **образ**? Это не «диск виртуалки», а набор **слоёв** файловой
системы, сложенных друг на друга через технологию **overlayfs** (copy-on-write):

```bash
docker history my-web-app             # посмотреть слои образа
```

```
IMAGE      CREATED BY                          SIZE
d4e5f6..   COPY app.py /app/                   2.1kB    ← наш слой
a1b2c3..   RUN apt install python3             45MB     ← слой с зависимостями
base..     FROM ubuntu:22.04                   77MB     ← базовый слой
```

Читаем снизу вверх: базовый слой Ubuntu, поверх — слой с установленным Python,
поверх — наш код. Каждая инструкция в сборке добавляет слой. При запуске
контейнера сверху докладывается тонкий **записываемый** слой — все изменения
контейнера пишутся туда, а базовые слои остаются нетронутыми и **общими** для всех
контейнеров из этого образа. Поэтому 10 контейнеров из одного образа не занимают
10× места — базовые слои переиспользуются. Вот откуда лёгкость контейнеров.

## 8. systemd: PID 1 хоста и менеджер сервисов

Мы видели, что внутри контейнера PID 1 — это приложение. А кто PID 1 на **самом
хосте**? В большинстве современных Linux — это **systemd**, первый процесс,
который ядро запускает при загрузке, и родитель всех остальных.

```bash
ps -p 1 -o pid,comm                   # что за процесс имеет PID 1 на хосте
```

```
PID  COMMAND
  1  systemd
```

systemd управляет сервисами через **юниты** — файлы с описанием «что и как
запускать». Основные типы юнитов:

- `.service` — сервис (демон), например наш веб-сервер;
- `.socket` — сокет, по обращению к которому поднимается сервис;
- `.timer` — запуск по расписанию (замена cron);
- `.target` — группа юнитов (например, «сетевой уровень готов»).

Посмотрим на статус сервиса — и обратите особое внимание на последнюю строку:

```bash
systemctl status web-42.service       # статус нашего сервиса
```

```
● web-42.service - Learning Web App
     Active: active (running) since Mon 2025-05-12 10:00:01
   Main PID: 48231 (my-web-app)
     CGroup: /system.slice/web-42.service
             └─48231 /usr/bin/my-web-app
```

Две вещи связывают этот вывод со всей лекцией:

1. **Main PID: 48231** — тот же самый PID, что мы видели у `web-42` на хосте в
   разделе 3! (В нашем сценарии приложение запущено и как сервис systemd.)
2. **CGroup: /system.slice/web-42.service** — systemd поместил сервис в
   **собственный cgroup**. Это тот же механизм из раздела 4, которым Docker
   ограничивал память. systemd использует cgroups, чтобы отслеживать и
   ограничивать каждый сервис. Один механизм ядра — два разных пользователя
   (Docker и systemd).

Более того, systemd умеет запускать и полноценные контейнеры —
`systemd-nspawn` создаёт namespaces точно так же, как Docker и как наш `unshare`.
Всё сводится к одним и тем же примитивам ядра.

## 9. Оркестрация: k3s / Kubernetes

Один контейнер на одной машине — понятно. Но в реальности их сотни, на десятках
машин, и они падают, обновляются, масштабируются. Управлять этим руками
невозможно — нужен **оркестратор**. Самый известный — **Kubernetes** (k8s).

Что даёт оркестратор поверх контейнеров:

- **планирование** — сам решает, на какой машине (ноде) запустить контейнер;
- **самовосстановление** — контейнер упал, k8s поднимает новый;
- **масштабирование** — «хочу 5 копий» → k8s поддерживает ровно 5;
- **сеть и обнаружение** — сервисы находят друг друга по именам.

Основные компоненты (обзорно):

- **api-server** — единая точка входа, вы общаетесь с ним;
- **etcd** — база, где хранится всё желаемое состояние кластера;
- **scheduler** — выбирает ноду для нового контейнера;
- **kubelet** — агент на каждой ноде, реально запускает контейнеры;
- **kube-proxy** — настраивает сеть/маршрутизацию (внутри — те же iptables!).

Запускает контейнеры kubelet не сам, а через **CRI** (Container Runtime
Interface) — стандартный интерфейс к containerd/runc. То есть в самом низу
Kubernetes — **те же runc, namespaces и cgroups**, что мы разбирали всю лекцию.

Центральное понятие k8s — **Pod**. Это не контейнер, а **группа контейнеров,
которые делят один network namespace** (и потому видят друг друга по
`localhost`). Вспомните лекцию про сеть: раз они в одном net namespace — у них
общий сетевой стек, общий IP. Pod — это буквально несколько процессов в одном
сетевом namespace. Снова тот же примитив.

**k3s** — это облегчённый Kubernetes: один небольшой бинарник вместо россыпи
компонентов, etcd заменён на лёгкую базу. Идеально для учёбы, edge-устройств и
маленьких серверов. API тот же, что у «большого» k8s, — поэтому учиться удобно
на k3s, а навыки переносятся на промышленный кластер.

Развернём один под в k3s, чтобы увидеть связь с самым началом лекции:

```bash
kubectl run web-42 --image=my-web-app        # попросить k3s запустить под
kubectl get pod web-42 -o wide               # посмотреть, что получилось
```

```
NAME     READY   STATUS    IP           NODE
web-42   1/1     Running   10.42.0.7    learnserver
```

Под `web-42` запущен, получил IP `10.42.0.7` (адрес из внутренней сети кластера —
её раздают CNI-плагины, но в основе снова network namespaces из прошлой лекции).
Мы прошли полный круг: от процесса с PID 1 до пода в кластере — и на каждом
уровне под капотом одни и те же namespaces и cgroups.

## Итоги

- **ВМ** несёт своё гостевое ядро (тяжело, но полная изоляция); **контейнер**
  делит ядро хоста (легко, изоляция слабее). Мы доказали общее ядро через
  `uname -r`.
- Контейнер = **процесс + namespaces + cgroups + capabilities**, а не «лёгкая
  ВМ» и не «отдельная ОС».
- **namespaces** = «что видно» (свой PID 1, свой hostname, своя сеть); мы
  показали, что PID 1 внутри — это обычный PID снаружи.
- **cgroups** = «сколько можно» (лимит памяти/CPU); один механизм используют и
  Docker, и systemd.
- **capabilities** = root, разобранный на части; root в контейнере ≠ root на
  хосте.
- Мы собрали контейнер руками через `unshare` — Docker (`docker→dockerd→
  containerd→runc`) автоматизирует ровно это, по стандарту OCI, а образ — это
  слои overlayfs.
- **systemd** — PID 1 хоста, менеджер юнитов, кладёт каждый сервис в свой cgroup.
- **k8s/k3s** оркеструют контейнеры поверх тех же примитивов; **Pod** — группа
  контейнеров в одном network namespace.

## Вопросы для размышления

**1.** В разделе 3 мы видели, что `my-web-app` имеет PID 1 внутри `web-42` и PID
48231 на хосте, а в разделе 8 у сервиса `web-42.service` в `systemctl status`
Main PID оказался тем же **48231**. Опираясь на это совпадение и на схему из
раздела 2, объясните: означает ли одинаковый PID 48231, что процесс «сидит
одновременно и в контейнере, и в systemd-сервисе»? Как вообще один процесс может
фигурировать в двух местах с разными PID (1 и 48231) — и что это говорит о том,
где процесс «на самом деле» живёт?

**2.** В разделе 5 мы, будучи root внутри `web-42`, получили отказ на команду
`date -s` (нет `CAP_SYS_TIME`). Теперь вспомните из лекции про права, что
системное время — общий ресурс всей машины. Свяжите два факта: **почему** для
контейнера особенно важно, чтобы именно `CAP_SYS_TIME` был отобран, даже если
внутри мы root? Что случилось бы с соседним контейнером `web-42`… простите, с
любым **другим** контейнером на этой же машине, если бы один контейнер мог
перевести часы? (Подсказка: сколько ядер у этих контейнеров — вспомните раздел 2.)

**3.** В разделе 6 мы собрали «контейнер» через `unshare` с флагами `--pid`,
`--mount`, `--uts`, но **не** указывали `--net`. Опираясь на таблицу namespace из
раздела 3 и на прошлую лекцию про сеть, предположите: какую сеть будет видеть наш
самодельный контейнер — свою изолированную или хостовую? Сможет ли он, например,
увидеть в `ss -tlnp` тот же nginx на `0.0.0.0:80`, что и хост? Объясните, чем
из-за отсутствия `--net` наш ручной контейнер отличается от `web-42`, которому
Docker net namespace создал.

**4.** Соберите общую нить лекции. Мы видели один и тот же механизм **cgroups** в
двух местах: Docker ограничил память `web-42` (раздел 4), и systemd поместил
`web-42.service` в cgroup (раздел 8). Мы видели один и тот же механизм
**namespaces** в трёх местах: net namespace в прошлой лекции, pid namespace в
нашем `unshare` (раздел 6), и network namespace внутри Pod'а k8s (раздел 9).
Исходя из этого, сформулируйте своими словами: почему фраза «Docker, systemd и
Kubernetes — это три совершенно разные технологии» является **неточной**? Что у
них общего на самом нижнем уровне, и кто этот «общий знаменатель»?
